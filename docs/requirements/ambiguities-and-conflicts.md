## Operator-resolved questions (were "unresolved" in v0.1)

- **UQ-001 First paying persona — RESOLVED.** Power users / developers **with institutional sight**: crypto-heavy users (crypto-Twitter-heavy traders holding several wallets) who benefit from streamlined cold/warm/hot management; NFT collectors, traders, creators; developers needing granular, CLI-integrated access to many chains incl. test/devnets. Positioning: a niche product that earns traction with heavy users but with UI/UX appealing to newcomers and latecomers choosing their first self-custody wallet — target review: *"the best modular self-custody, open-source wallet, for both newcomers and seasoned pros."* → Drives W2 UI priorities (vault tiers, network profiles, CLI parity) — recorded in roadmap.
- **UQ-002 Warning-fatigue design — RESOLVED (design directive).** Flag obvious and semi-obvious risky transactions; power users can minimize warnings (timer / per-address / per-transaction, per US §16). **Hard-code non-overridable hard stops where the outcome is inevitable fund loss** — e.g. sending USDC from an Ethereum account to a Solana address, or Ordinals to an incompatible Bitcoin address: chain-family confusion that is a non-obvious trap for newcomers and an easy slip for seasoned operators; blocked at code level because the only possible outcome is loss. → New requirement **CL-POL-009 (hard-stop class: deterministic BLOCKED, no override path)**. Note: today's EVM-only validation already rejects malformed EVM addresses; the general cross-chain-family checks land with multi-chain support and must ship *with* each new chain adapter.
- **UQ-003 Non-spoofable confirmation surface on macOS — RESOLVED (direction).** Prefer the strongest available tier first — **Secure Enclave Processor (SEP)-backed** confirmation/attestation on Apple-silicon — degrading through lower-level techniques for Intel-era Macs. → Recorded in the browser repo's trusted-confirmation-surface requirements; requirement CL-VLT-009 added.
- **UQ-004 License selection — RESOLVED (operator decision, 2026-07-16).** Apache-2.0 across all four repos (family, wallet, browser, scam-guard), plus a DCO (`Signed-off-by`) contribution requirement. → `LICENSE` + `CONTRIBUTING.md` added in each repo; `license`/`license.workspace` set in every Cargo.toml; `LICENSE-TBD.md` removed. Analysis that preceded the decision: family repo `LICENSE-RECOMMENDATION.md`.
- **UQ-005 Browser packaging — RESOLVED.** The browser ships **as its own binary**, structured as modular packages: `browser-core` (library: rendering setup, security settings, ad-blocking/privacy config, UI design tokens) · `standalone-browser` (binary: browser frame, tabs, bookmarks, address bar) · `wallet-app` (binary embedding `browser-core` as a dedicated web-view mode with the wallet provider injected natively). Distribution: **Mode A (embedded engine) is the baseline default; Mode B (symbiotic — linking against the installed standalone browser) is an opportunistic optimization**, with strict guardrails: code-signature enforcement (`codesign -v` / WinVerifyTrust against our developer certificate) and version-matrix matching with automatic fallback to Mode A. **Governance resolution (operator choice 2026-07-05):** to preserve the dependency direction (wallet must not depend on browser internals), `browser-core` and *both* suite binaries are built from the **browser repo** (which imports wallet exports); the pure wallet app stays in the wallet repo. Full technical treatment: `browser/docs/architecture/packaging-and-distribution.md`.
