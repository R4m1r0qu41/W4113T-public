# ADR-019 — Browser-Connect v0.4: Typed-Data/Message Signing + Read-Only RPC Proxy

**Status:** Accepted (implemented) · **Date:** 2026-07-16 · **Decider:** operator · Closes AC-C end-to-end (browser threat-model abuse case, "the permit harvest") and CL-EVM-003; extends the v0.3 host-attested transport (ADR-013). Additive-only over v0.3 — v0.3-shaped clients keep working unchanged.

## Context

The browser repo's real-dapp compatibility audit (`docs/testing/dapp-compat-matrix.md`, evidence document, not a design doc) measured what a real production dapp's `window.ethereum` calls would hit against the shell as it stood: four methods worked (`eth_requestAccounts`, `eth_accounts`, `eth_chainId`, `eth_sendTransaction`); six pure chain-state reads were denied with no signing consequence (`net_version`, `eth_call`, `eth_estimateGas`, `eth_blockNumber`, `eth_getBalance`, `eth_getTransactionReceipt`/`eth_getTransactionByHash`); and, most consequentially, `eth_signTypedData_v4` and `personal_sign` were **hard-broken** — not degraded, broken outright — because they were blocked at three independent layers at once: broker-core never classified them, the browser-connect envelope had no shape to carry them, and (per this repo's own `requirements-matrix.md`, CL-EVM-003) full EIP-712 parsing was itself only partial.

By 2026-07-16, the third layer had already closed: `cipherlayer-evm::typed_data` (library-level, landed in an earlier pass) computes the real EIP-712 signing hash and classifies EIP-2612/DAI-style permits, feeding the existing unlimited-approval policy path — but only as a library, exercised by security-regression tests calling the policy engine directly. CL-EVM-003's own status note was explicit about what remained: *"Honest bound: library-level only — no production request path carries typed data yet... Closing end-to-end needs the typed-data request path (browser-connect contract rev + serve wiring)."* That is this ADR.

Separately, the compat matrix's own disposition table drew a sharp, correct line: the six read-only methods are "pure proxy candidates: forward to the wallet's existing read path... no new pipeline stage, no new confirmation surface" — structurally different from `eth_signTypedData_v4`/`personal_sign`, which "must traverse a real decode→simulate/interpret→risk→policy→USER_REVIEW path... the same discipline `eth_sendTransaction` already gets." This rev treats them accordingly: one gets full pipeline treatment, the other gets a narrow, whitelisted proxy with no pipeline at all.

## Decision

Three additive changes, protocol v0.3 → **v0.4**:

### 1. Typed-data signing (`eth_signTypedData_v4`)

`transaction-request-envelope.v1` payload gains `kind` (`evm_transaction` default | `typed_data` | `personal_message`) and `typed_data_json`/`message_hex`. A `typed_data` request runs through the **same** pipeline as a transaction: `cipherlayer-provider::validate` format-checks and parses the payload (fail-closed on malformed input, mirroring calldata's hex-decode gate); the pipeline's Decoded step re-parses via `cipherlayer_evm::typed_data::parse_typed_data` and projects the result into the same `Decoded`/`ActionKind` shape calldata decoding produces — so a permit hits `POL-APR-001` (unlimited default-deny) exactly like an on-chain `approve`, and anything that doesn't match a recognized permit shape classifies `unknown` at `Confidence::Unknown`, hitting `POL-UNK-001` (restrictive, escalate-or-deny by policy) — never a quiet "Sign" prompt. This is the literal AC-C closure: *"Undecodable typed data ⇒ unknown classification ⇒ escalation, never a quiet Sign prompt."*

The EIP-712 domain's `chainId`, when present, is compared against the session/envelope chain (`TypedDataDomain::chain_id_matches`, already existed at the library level); a definite mismatch is a new deny rule, `POL-CHAIN-002` — the same cross-chain-replay discipline as AC-D, applied to signatures. A domain that omits `chainId` (legal per EIP-712) is not flagged (honest "not verifiable"), following the schema convention that absence is not a match.

Simulation cannot apply — there is no on-chain transaction — and the pipeline never fakes one: a new `SimulationStatus::NotApplicable` (distinct from `Unavailable`) records "evaluated and out of scope" rather than "should have simulated and couldn't." The distinction has teeth: `Unavailable` still forces the restrictive unknown-action path; `NotApplicable` does not, so a well-classified, bounded permit is not force-escalated purely for lacking simulation evidence it was never supposed to have. Chain-identity verification against the live RPC node is likewise skipped for signature-only kinds — nothing downstream (no nonce fill, no gas fill, no broadcast) depends on that RPC data, so there is nothing to poison and no reason to require Anvil for this flow at all.

The Vault gains a `message_payload` on `VaultSigningRequest`: `TypedData { typed_data_json }`. It **re-parses and re-hashes the payload itself** rather than trusting a pipeline-supplied digest (`cipherlayer_evm::typed_data::parse_typed_data` runs inside `cipherlayer-vault` too — a new intra-workspace dependency, not an external one). This is the same "never blind-sign a hash" discipline that already keeps raw `eth_sign` forbidden: the Vault only ever signs a digest it derived from a payload it parsed and understood, never an opaque value a caller hands it. `Vault::authorize_and_sign` now returns `SignOutcome::{Transaction, Message}`; the message case produces a 65-byte r/s/v signature via `alloy::signers::Signer::sign_hash` over the EIP-712 digest. `signing-request.v1`'s `payload.kind` enum already reserved `typed_data`/`personal_message` (schema-level, unimplemented); this rev wires the Rust side (`WirePayload`, `into_request`, the daemon) to match.

The pipeline terminates such a request at `SIGNED` — there is no broadcast step for a signature. This is not a shortcut around the signing state machine: `LifecycleState::Signed`'s transition table (`Signed => Broadcast | BroadcastFailed`) is untouched, and this ADR does not add a state or an edge. A request simply stops advancing once it reaches a legal state that happens to be its correct terminus; `is_terminal()` was already list-based, not inferred, so nothing needed to change there either. `signing-response.v1` gains `signature_hex` (v1.3) to carry the result.

### 2. `personal_sign`

`personal_message` follows the identical pipeline shape. Decoding is deterministic and total (unlike typed data, there is no unrecognized-shape case): valid UTF-8 is shown as readable text; otherwise the raw hex is shown — never mangled, never dropped. It always reaches USER_REVIEW like every other signing request (nothing about `personal_sign` grants a bypass), and the Vault hashes the message itself via the standard EIP-191 personal-message construction (`alloy::signers::Signer::sign_message`) — again, never a caller-supplied hash. Raw `eth_sign` (sign an arbitrary caller-supplied hash with no message context) stays exactly as forbidden as before; nothing in this rev creates a path to it.

### 3. Read-only RPC proxy (`rpc_query`)

A new, separate wire message — **not** a `transaction-request-envelope` payload kind, and deliberately not routed through the signing pipeline at all, because it has no signing consequence to gate. A **STRICT hardcoded whitelist** of eight methods: `eth_call`, `eth_estimateGas`, `eth_blockNumber`, `eth_getBalance`, `eth_gasPrice`, `eth_getTransactionByHash`, `eth_getTransactionReceipt`, `net_version` — exactly the compat matrix's "must-forward read-only" list, no more. None of these can move funds, change permissions, or produce a signature; the whitelist is the entire safety argument, and it is not caller- or config-extensible (`RPC_QUERY_WHITELIST` is a `const` in `serve.rs`, checked before anything else, including before the origin/capsule identity check). Anything off the list is refused with the transport's existing `malformed_or_unsupported` code — the same deny-by-default idiom the transport already uses for unrecognized messages — never forwarded.

`rpc_query` is capsule-bearing (carries `origin`/`capsule_id`) and therefore requires host attestation (ADR-013), exactly like `connect_request`/`transaction_request`. It requires an active permission grant — read-only class suffices, and a signing-class grant also suffices (`PermissionStore::has_any_active`, chain-scoped, access-class-agnostic) — because a read carries no more authority than either grant already implies. Both the request `params` and the RPC `result` are independently size-bounded (16 KiB / 256 KiB — tighter than the general envelope cap, since legitimate params for these eight methods are always small). Execution is against the wallet's own configured RPC endpoint for the requested chain, never a caller-supplied endpoint.

**No per-query audit event is emitted.** This is a deliberate call, not an oversight: these are high-volume, no-consequence reads — a wagmi/viem client can poll `eth_blockNumber` or `eth_call` several times a second — and logging every one would flood the hash-chained audit log with routine traffic that has no forensic value (the whitelist already bounds what could possibly have happened; there is nothing to investigate afterward that isn't already implied by "a grant existed and this method is on the list"). The audit log's job is decision provenance for consequence-bearing events — grants, denials, signatures — and diluting it with poll traffic would make it *harder*, not easier, to find the events that matter. Connection-level enforcement (attestation, permission, whitelist, size caps) still applies identically on every call even though it is not separately logged per call.

## What is deliberately NOT in this rev

`wallet_switchEthereumChain` and `wallet_addEthereumChain` are consequence-bearing in a way this rev's typed-data/message-signing work is not: they change which chain a site's subsequent requests are scoped to, and `per-site-permissions.md` already describes a design ("chain-switch requests outside the allowlist prompt") that is not yet reconciled with any shipped implementation (the compat matrix flagged this gap explicitly). Wiring a mechanical forward for these methods now — ahead of that design being settled — would let the wire move faster than the security model it's supposed to express, which is exactly the failure mode `AGENTS.md`'s "do not broaden scope silently" rule exists to prevent. They are deferred to a dedicated per-site-permissions design pass, not dropped.

`wallet_watchAsset` and `wallet_getPermissions`/`wallet_requestPermissions` (EIP-2255) stay deferred per the compat matrix's own disposition (cosmetic / low real-world incidence) — no new information in this rev changes that call.

The Vault-side confirmation surface (`cipherlayer-vaultd`'s desktop trusted surface, `--vault-confirm`) is **not** extended to typed_data/personal_message in this rev: `WireDisplayEvidence` is transaction-shaped (to/value/simulation), and approximating a display for a signature request risks rendering something misleading rather than nothing. A message-signing request under `ReviewMode::VaultSurface` is refused outright (fail-closed, coded, documented) rather than rendered incorrectly; the direct review path (`--yes`/interactive) is unaffected and is what closes AC-C end-to-end today. Extending the trusted surface to signature payloads is real design work (what should a permit/message confirmation dialog show?), tracked as a follow-up, not squeezed into this rev.

## Consequences

- Schemas: `transaction-request-envelope.v1` → v1.1 (additive: `payload.kind`, `typed_data_json`, `message_hex`; `to` no longer required); `signing-response.v1` → v1.3 (additive: `signature_hex`); `vault-signing-response.v1` → v1.1 (additive: `signature_hex`, `VLT-MSG-001`); `transaction-intent.v1` → v1.1 (additive: `domain_chain_id_matches`); `policy-decision.v1` → v1.1 (additive: `evidence_considered.simulation` gains `not_applicable`); new `rpc-query.v1`. `signing-request.v1`'s `payload.kind` enum was already forward-looking (schema-level `typed_data`/`personal_message` predate this rev); this closes the Rust-side gap between that schema and `cipherlayer-vault::ipc`, which previously implemented `evm_transaction` only.
- `WalletCapability::current()` advertises `protocol_versions: [0.1, 0.3, 0.4]` and `methods` gains `rpc_query`; `connect serve`'s live `PROTOCOL_VERSION` advances to `"0.4"`.
- Export bundle `exports/browser-connect-v0.1/` refreshed in place (protocol doc + the five changed schemas + new `rpc-query.v1.json`), SHA256SUMS regenerated — same bundle directory/version label ADR-013/ADR-014 already refreshed in place; the directory name is the export channel identifier, not the protocol version.
- Requirements matrix: CL-EVM-003 moves from "partial (parser done)" to done end-to-end (typed-data request path exists: browser-connect contract + serve wiring + Vault signing). CL-PRV-003 updated for v0.4.
- New security-regression tests (`crates/cipherlayer-cli/tests/security_regression.rs`, `crates/cipherlayer-vault/src/{lib,ipc}.rs`, `crates/cipherlayer-cli/src/serve.rs`) exercise the full pipeline end to end for both new payload kinds and the RPC whitelist — deliberately without requiring Anvil, since neither typed_data/personal_message signing nor the RPC-whitelist-rejection paths touch chain RPC at all.

## Alternatives considered

1. **Carry the pre-computed EIP-712 hash to the Vault instead of the raw JSON** — rejected: it would make the Vault (in-process or the separate `cipherlayer-vaultd` process) blind-sign an opaque digest exactly like the forbidden `eth_sign`, contradicting the crate's own stated "trust nothing upstream" discipline.
2. **Route `rpc_query` through the signing pipeline as a fourth payload kind** — rejected: it has no signing consequence, so decode/risk/policy/USER_REVIEW stages would be pure overhead (and the compat matrix already drew this line); a separate, narrower wire message with a hardcoded whitelist is a smaller, more auditable surface.
3. **Emit an audit event per `rpc_query` call** — rejected for the reasons stated above (volume vs. forensic value); revisit if a future need for read-path forensics (e.g., detecting reconnaissance patterns) emerges — the whitelist enforcement itself would still need to change first, since that is what actually bounds the read surface.
4. **Extend the Vault-side confirmation surface to message-signing now** — rejected: real design work (what a signature confirmation dialog shows) that would either delay this rev or ship a wrong/misleading first cut; deferred as its own follow-up with the direct review path covering the gap in the meantime.

## Revisit

When per-site-permissions design lands, revisit `wallet_switchEthereumChain`/`wallet_addEthereumChain` as their own contract rev. When the Vault-side confirmation surface is extended to message payloads, revisit the `ReviewMode::VaultSurface` refusal added here. If `rpc_query` traffic patterns turn out to carry forensic value (e.g., a scam site probing many addresses before ever asking for a signature), revisit per-query audit logging then, not preemptively.
